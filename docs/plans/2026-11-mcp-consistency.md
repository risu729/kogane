# Plan: one paging contract and consistent arguments across the MCP tools

- Status: **proposed** (2026-11-20). The owner asked on 2026-11-20 to "unify the paging method, and fix
  the other places that are needlessly inconsistent" across the MCP tools and their routes. The design
  is [ADR 0128](../adr/0128-one-paging-contract.md) (proposed); every change to a published tool's
  arguments, results or refusals needs the owner's approval before merge. Slice S1 (the shared contract
  and the tools no in-flight branch touches) is implemented on the same branch as this plan; the other
  slices are proposals, ordered below.
- Baseline: main at `40553eedb` (#1400), 53 published tools.
- Duplicate check (2026-11-20): no ADR, plan or branch unifies paging. ADR 0119 (a snapshot cursor
  continues at another page size), ADR 0123 (`mustMatch` on `cursor_mismatch`), ADR 0081's 2026-11-07
  amendment (`nextPage`) and ADR 0127 (`next.after`) each settle one read; this plan builds on all four
  and replaces none of their bindings. The highest ADR number on main or on any remote branch is 0127
  (0121 and 0122 are unused, 0124 and 0126 are on branches), so this design takes 0128.

## Why

The MCP protocol pages only its list methods (`tools/list`, `resources/list`, ...). A `tools/call`
result has no protocol paging, so each kogane read pages through its own arguments and its own result
fields, and today each does it its own way: an agent has to learn, per tool, which argument continues
(`cursor`, `offset`, `latestOffset`, `after`), which field names the next page (`nextCursor`,
`nextOffset`, `latestNextOffset`, `coverage.nextOffset`, `page.nextCursor`, `data.nextCursor`,
`next.after`, a `cursor` result field), how it says rows follow (`truncated`, `hasMore`, `nextPage`,
`complete`, `cut`, a non-null token) and which refusal a stale token gets (`400 cursor_mismatch`,
`409 stale_context`, `400 invalid_query`, `404 receipt_not_found`, `410 context_expired`). A client
that guesses wrong does not fail loudly: it stops early and reads a partial list as the whole one.

## 1. Inventory: how each published tool pages today (main `40553eedb`)

Abbreviations: **K** keyset (position = last row's sort key), **O** offset (position = row count),
**I** id (position = last row's id, not bound to anything). "Bound" is what a token is checked against;
"digest" means a hash of the bound inputs carried in the token and compared, never a signature. No
token anywhere is signed: each is base64url of a JSON shape the server re-checks
(`packages/domain/src/paging.ts:170-175`), or plain text.

### Ordering with events-filters

S1 converts `events.read` on main's unfiltered offset pages; the events-filters branch adds a
filtered activity list paged by a keyset `cursor`, where `walk.bound` can end a page early. The two
conflict in `services/app/src/events-api.ts` and in the `events.read` description in
`page-read-tools.ts`. Whichever merges second resolves it: if events-filters merges first, S1 is
rebased so a filtered page answers `next: {arguments: {cursor}}`; a page the walk bound ended
early has no stop reason in the contract (`limit`, `bytes` and `budget` each mean something else),
so it needs a decision before the second of the two merges; if S1 merges first, events-filters adds `next` and
`paging` to its filtered branch, and its walk tests follow `next.arguments`. Moving `events.read`
out of S1 into its own slice after events-filters avoids the conflict entirely.
